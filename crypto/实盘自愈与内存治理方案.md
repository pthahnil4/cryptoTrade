# 实盘自愈与内存治理方案

> 落地日期：2026-09-10　|　运行环境：2 核 2G 云服务器 + 宝塔 Python 项目管理器（supervisord）
> 关联代码：`crypto/process_lifecycle.py`（新增）、`crypto/memory_watchdog.py`、
> `crypto/task/scheduler.py`、`crypto/task/memory_daily_reset.py`（新增）、`crypto/app.py`、
> `crypto/templates/system_status.html`
> 冒烟：`crypto/task/_smoke_boot_resume.py`（🔒 纯离线 47 项）、`crypto/task/_smoke_trading_runtime.py`（18 项）

---

## 1. 要解决的两个问题

| 问题 | 结论 |
|---|---|
| 内存涨到 800MB 就自杀重启，2G 机器上合不合理？ | **合理，且不下调**（按用户要求保持 warn 600 / kill 800）。实测运行带 170–355MB，800MB 距峰值仍有 445MB 余量，见 §7 |
| 重启后定时任务不会自动打开 | 根因不是"没写自愈代码"，而是**进程分不清自己是怎么起来的**：原来只有 `first_run` 一种认知，凡是读不到期望状态就当初次上线，绝不自动下单。现在补上归因层，再按时间窗分流处置，见 §3–§4 |

说明一下"定时任务"的两种口径：`BackgroundScheduler` 里的行情巡检、账单同步、告警监控等任务，
进程起来就会自动注册并运行，本来就不需要人工；**真正需要自愈的只有实盘交易调度器**
（`TrendRangeTrader` 那条链），本方案处理的就只有它。

## 2. 一句话架构

```
退出前落原因                              起来后判原因                  按原因+钟点决定动作
memory_watchdog   ─┐ hard_exit()          proc_exit.json ─┐
daily_reset       ─┤ ─────────────────→                    ├→ classify_boot → plan_resume → _auto_resume_worker
SIGTERM 面板停止  ─┘ 只写标记，再把终止交还系统   memory_history.jsonl ─┘  五态归因      决策矩阵      起 / 延时起 / 熔断只发信
（kill -9 / 崩溃来不及写）                          boot_ledger.jsonl ─┘  熔断计数

三层各自独立，任何一层坏掉都退回改造前的行为：**不自动拉起**。
自动下单是不可逆动作，宁可比人晚起十分钟，也不能替用户做出下单决定。

## 3. 启动归因（P0-B）

### 3.1 三个状态文件（都在 `crypto/logs/`，可用 `CRYPTO_LIFECYCLE_DIR` 整体改址）

| 文件 | 谁写 | 作用 |
|---|---|---|
| `proc_exit.json` | 三个写入点：看门狗撞线、每日归零（都走 `hard_exit`）、SIGTERM（`install_sigterm_marker`）。写入用 tmp + `os.replace` + fsync 原子落盘 | 记下"我是自杀还是被杀"，附 RSS、阈值、触发源 |
| `memory_history.jsonl` | 看门狗 / 系统监控每轮追加（已有） | 当心跳用：有最近的心跳却没有退出标记 ⇒ 被外力瞬间干掉 |
| `boot_ledger.jsonl` | 每次启动归因后追加一行 | 重启风暴熔断的计数依据 |

### 3.2 五种归因与判定顺序

判定按顺序短路，先判标记再看心跳：

| 顺序 | 条件 | 归因 | `BOOT_LABELS` 中文名 |
|---|---|---|---|
| 1 | `proc_exit.json` 新鲜（≤900s）且未被消费，reason=`mem_kill` | `mem_restart` | 内存超限自愈重启 |
| 1 | 同上，reason=`daily_restart` | `daily_restart` | 每日主动归零重启 |
| 1 | 同上，其它 reason（如 SIGTERM 写的 `manual_exit`） | `cold_start`（detail 带上原始 reason） | 冷启动（人工/面板/开机自启） |
| 2 | 无标记，但有效心跳距今 ≤420s，且**最近一条带 pid 的心跳**作者仍存活 | `parallel_instance` | 并发实例（旧进程还在跑） |
| 2 | 无标记，但有效心跳距今 ≤420s（作者已死 / 判不出作者） | `abnormal_death` | 异常死亡后重启（崩溃/被系统杀） |
| 3 | 从来没有过有效心跳 | `first_run` | 初次启动 |
| 4 | 有心跳但已停在 420s 之前 | `cold_start` | 冷启动（人工/面板/开机自启） |
| — | 归因过程抛异常 | `unknown` | 启动原因未知 |

**第 2 类是本次真正的增量**：代码崩溃、被内核 OOM `kill -9`、被 SIGKILL 强杀，都来不及写标记。
改造前它们和"初次部署"长得一模一样（都是"没标记 + 没期望状态"），所以永远不起来；
现在靠"刚才还在写心跳，这一秒没了"把它单独识别出来 —— 这也是用户坚持不降阈值后必须补的一层：
阈值越高越容易先撞上内核的 OOM killer，那条路不会有 `mem_kill` 标记。

### 3.3 SIGTERM：面板重启不该记成事故

人在宝塔面板点「重启」，supervisord 发的是 SIGTERM。不接的话，心跳停在刚刚、又没标记
→ 归因成 `abnormal_death`，于是**每次人工重启都会收到两封长得像事故的信**（预告 + 接回结果），
收信人还会以为程序崩了。处理办法：`install_sigterm_marker()`（`app.py` 导入阶段在主线程装）
先落一枚 `manual_exit` 标记，下次启动就归到 `cold_start`（处置完全不变，只是标签不骗人）。

两个硬约束，写进代码也写进了冒烟：

- **绝不吞掉停止请求**：注册 handler 后 Python 默认的"立即终止"不再发生，所以 handler
  必须恢复 `SIG_DFL` 再给自己重发同一次信号（A6 专门断言这一步）—— 面板停不掉进程
  比归因不准严重得多。
- **信号上下文里不打日志、不读 RSS**：handler 跑在主线程字节码边界上，若恰好打断了
  另一处写日志的动作，再进 `logging` 就是拿不可重入锁，会当场挂死（连标记都写不出去）。
  所以走 `write_exit_marker(quiet=True)`，且只写一个几百字节的 JSON。
- 只抓 SIGTERM，**不抓 SIGINT**：本地 Ctrl+C 靠 `KeyboardInterrupt` 收尾，抢掉它会带来新问题。
- 若已有别的组件占了 SIGTERM（某些 WSGI 服务器），我们**不抢它的语义**，直接放弃安装（A7）。

### 3.4 四个必须避开的归因陷阱（冒烟 B4/B8/B9/B10 专门盯着）

1. **心跳来源要过滤**：只认 `source in ('app','embedded')`。`guard` 记录由独立 cron 写，
   交易进程早死了它照样每分钟落盘，拿它当心跳会把"死了几小时"判成"刚刚才死"。
2. **本进程自己刚写的心跳要排除**：用 `_BOOT_TS - 3s` 做 cutoff，否则初次启动会被自己那一行误判成异常死亡。
3. **退出标记只能用一次**：认领后写 `consumed_at`。不然撞内存起来后紧接着再崩一次，
   第二次仍会读到同一份新鲜标记，被误判成"又是内存超限"。
4. **过期标记不认领**（>900s）：那是上一次重启已经消费过的旧账，会把几天前的动作安到这次头上。

## 4. 自愈决策矩阵（P0-C）

| 启动原因 | 时段 | 动作 | 邮件 |
|---|---|---|---|
| `first_run` 初次上线 | 任意 | **不起** | 不发（没人在等它） |
| `daily_restart` 每日归零 | 任意 | 20s 后接回 | **全程静默**（天天发信一周就把告警看麻了） |
| `mem_restart` / `abnormal_death` | 夜间 00:00–08:00 | **20s 后直接接回**（人在睡觉，早接早少漏单） | 接回结果一封 |
| 同上 | 白天 08:00–24:00 | **先发预告信 → 等 600s → 再接回** | 预告 + 结果各一封 |
| `cold_start` 面板重启/发版 | 按所在时段 | 同上按时间窗处理（面板优雅重启带 `manual_exit` 标记，不会误标成崩溃） | 同上 |
| `parallel_instance` 并发实例 | 任意 | **不起**（两个调度器对同一账户会重复开仓），**不占熔断额度** | 发一封"多开了一个实例，实盘没停" |
| `unknown` / 归因层不可用 | 任意 | 不起（保守方向） | 若实盘本应在跑则发"请手动启动" |
| 熔断触发 | 任意 | 不起 | 发一封"为什么不再自动起" |

白天那 600s 不是白等，它是**人工否决窗**，实现上不需要额外开关：

- 预告信先发出去 → 你有 10 分钟去页面看持仓和挂单对不对；
- worker 睡完才读 `desired_running`（不是睡之前）→ 期间你点了「停止交易」，本次拉起自动作废；
- 期间你点了「启动交易」→ `if self._trading_running: return` 让位给人工，不重复起。

### 重启风暴熔断

6 小时窗口内自愈类重启（`mem_restart` + `abnormal_death`）达到 **3 次**即停止自动拉起，只发信。
反复重启说明环境本身没修好（内存泄漏修不完 / 机器被别人抢 / 依赖崩），继续自动起等于在坏环境里反复真实下单。
计划内的 `daily_restart` 不占额度，窗口外的历史记录也不计入（冒烟 C8/C9/C10）。
熔断信不只说"不起了"，还带上下一步去哪查：`/system-status` 的内存趋势、必要时建
`logs/memtrace.on` 抓强退前的分配快照对比定位增长点，修好后再手动点「启动交易」（冒烟 C11）。

### 心跳很新 ≠ 上个进程刚死（2026-09-11 事故）

归因第 2 档的原话是"没有退出标记，但 6s 前还在写心跳 → 判定为异常死亡"。这句话
隐含了一个从未写进文档的前提：**写心跳的那个进程已经死了**。同机再起一个 `app.py`
（IDE 里顺手点运行、面板重启与新实例并存）时，新实例读到的新鲜心跳是那个**活着**
的实例写的，于是凭空认定"我是一次异常死亡之后的重启"：

- 每并发一次吃一格熔断额度。当天 17:38、18:05 两个误起的实例把额度吃到 4 条，
  **熔断跳闸**，此后真崩死也不会自动接回（要等窗口滑过），同时状态页上多出一条
  假的"异常死亡"；
- 更危险的是它的自愈计划是 `allowed=True`：白天等 600s 就会起**第二个调度器**，
  两个调度器对同一账户挂单/撤单。当天只是运气好 —— 那两个实例都在 600s 到点前
  因抢不到 6001 端口自己退了（双向核对过：日志轮次号在同一进程内没有回跳，
  交易所侧每币种恰好一笔挂单）。

修法：心跳记录里本来就带作者 `pid`，判活直接问操作系统（`psutil`），活着就归
`parallel_instance` —— 不占额度、不自动拉起、但**照样发信**（信里说清"实盘没停，
只是多开了一个实例，要重启请先停旧的"）。两个必须留意的细节：

1. **不能用"最新一条心跳"的 pid**：生产上最新一条几乎都是 `source: embedded`
   （应用内系统监控写的内存水位），它不带 pid；带 pid 的 `app` 行每分钟都比它早
   几秒。只看最新一条会让这条修复在真实数据上一次都不触发，而伪造数据的冒烟
   照样全绿。口径：判活看**最近一条带 pid 的心跳**，且它自己也得在 420s 内。
2. 探活只用 `psutil`（`pid_exists` + `create_time`），不用 `os.kill(pid, 0)`：
   它给不出出生时刻（挡不住 PID 复用），且本机 3.13.1 实测其行为与 `os.kill`
   文档相反（既不终止也不报错），跨版本语义不稳。拿不到结论时一律回落
   `abnormal_death` 保持改前行为 —— 宁可多算一次崩溃，也不能让该自愈的不自愈。

排查工具：`python crypto/task/_diag_process_instances.py`（只读，列实例数 / 端口
归属 / 启动台账 / 熔断余额与**解封时刻**）。解封时刻的口径是"窗口内老账只剩
`RESUME_MAX - 2` 条"，因为未来的那次重启自己还要再落一条账。

## 5. 每日内存主动归零（P1-B）

`crypto/task/memory_daily_reset.py`，cron 默认 **04:03**（错开整点，避开整点轮次）。

把"被动涨到 800 撞线"变成"每天在低波动窗口主动清零一次"。CPython 没有 JVM 式压缩 GC，
glibc 分配器棘轮 + pymalloc arena 残留会让 RSS 随累计轮数单调上升，`tune_glibc_allocator()` /
`malloc_trim` 只能压平一部分 —— 既然涨是必然的，就自己挑时刻归零，而不是等它撞在剧烈波动的那一分钟。

四条拒绝执行条件（任何一条成立今天就跳过，明天再来）：

| 条件 | 理由 |
|---|---|
| 读不到本进程 RSS | 不做不可逆动作 |
| `desired_running=True` 但「重启自动拉起」开关没开 | 此刻重启 = 亲手把实盘停掉且没人接手，等于制造静默停摆 |
| 策略引擎忙（`pro3_locked_now()`，最多等 300s） | 一轮 `analyze()` 中途被杀不污染交易所侧（挂单在服务器外、账本与反向风控计时都在 MySQL），但会把那轮的分析记录、成交确认留在半路 |
| RSS < 350MB | 内存没涨起来就别折腾，白白制造停摆窗口 |

## 6. 采样间隔：300s → 120s

阈值不动，但检查频率提高。原来 5 分钟一轮，2G 机器上一轮 `analyze()` 能吃掉上百 MB，
最坏情况是"上一轮 500MB 放行、这一轮已经 1.2GB 被内核杀了" —— 中间这段根本没人看。
120s 把盲区压到 2 分钟，且仍在"比 OOM killer 通常更快"的量级；开销是每轮多读一次 `/proc`，可忽略。

放弃的方案：`MemAvailable` 第二触发条件（机器整体吃紧就提前退）。理由：会把别人的内存问题算到自己头上，
在不降 kill 阈值的前提下反而更容易误杀，且引入新的不确定参数。

## 7. 阈值对照表：升到 4G / 8G 时 kill 线提到多少

**地板值校验法**：先看空闲基线 RSS（本进程刚起来、跑完一轮稳定后的水位），kill 线取 **地板值 × 4~5**。
只看"总内存的百分之多少"是不对的 —— 阈值管的是本进程涨多少算异常，和机器总内存只是间接关系。

实测依据（`crypto/logs/memory_history.jsonl` 全量 374 条 `app/embedded` 心跳）：
min 68.4 / 中位 174.3 / 均值 173.2 / p95 320.4 / max 354.5 MB。
即地板值约 170MB，×4~5 = 680~850MB，现有 800MB 正落在合理区间内 —— 这也是"不必下调"的量化理由。

| 机器内存 | 建议 warn | 建议 kill | 占总内存 | 备注 |
|---|---|---|---|---|
| 2G（现网） | 600 | **800** | 39% | 保持不动 |
| 4G | 1200 | 1500~1800 | 37~44% | 给系统页缓存与 MySQL 留够余量再抬 |
| 8G | 2500 | 3500~4000 | 43~49% | 若同机还跑 InfluxDB/多个项目，按剩余额度倒挤，不要按总内存正推 |

调的时候只改 `CRYPTO_MEM_WARN_MB` / `CRYPTO_MEM_KILL_MB`，不要改代码默认值（默认值是 2G 机器的标定）。

- 页面 `/system-status` 指标网格新增「本次启动归因」卡（异常死亡 / 原因未知标黄），

- 邮件正文新增「启动归因」行 + `boot #序号` + 窗口内自愈次数，让收信人一眼判断该不该担心。

## 10. 部署侧必须人工确认的三件事

1. **`/task` 页面的「重启自动拉起」开关要打开**（`auto_resume`）。这是总闸门，
   代码只负责决定"什么时候起"，不负责替你打开这个开关。关着的话，重启后会收到
   一封"实盘本应在跑但自动拉起开关未打开，请手动启动"的信。
2. **supervisord 的 `autorestart=true` 与开机自启**。整套拉起链路依赖外部管理器：
   进程 `os._exit(1)` 之后由它重新起。宝塔项目面板里确认勾选了"守护进程/自动重启"，
   并确认服务器重启后项目管理器自身会自启 —— 否则归因再准也没人拉起进程。
3. **supervisord 的 `stopsignal` 保持默认的 `TERM`**（宝塔项目配置里可看）。
   改成 `KILL` 的话 SIGTERM 捕获根本不会触发，面板重启又会被归因成异常死亡
   （处置不变，只是标签不准）。启动日志里没看到「已捕获 SIGTERM」这一行，
   就是这条链路没接上（非主线程导入、或已被 WSGI 服务器占了处理器）。

## 11. 验证方式

```

已用真实 `memory_history.jsonl` 副本验证过归因：心跳龄 180s + 无标记 → `abnormal_death`，
白天窗口计划为 `delay 600s + pre_notify`，且生产 `crypto/logs/` 未被测试写入。
`CRYPTO_NO_BACKGROUND=1` 下 `crypto.app` 可正常导入，`get_boot_info()` 返回 None。

上现网后建议两次演练（各一分钟）：

1. **撞线演练**：把 RSS 顶到阈值（或临时设 `CRYPTO_MEM_KILL_MB=200`）触发一次真重启，
   核对页面「本次启动归因」是否显示为内存超限自愈、以及是否按计划时间接回了实盘。
2. **面板重启演练**（验 SIGTERM 接住了）：在宝塔里点一次「重启」，起来后看
   `crypto/logs/proc_exit.json` 应为 `"reason": "manual_exit"`、页面归因应为

   这一步必须在服务器上验：Windows 本地 `os.kill(pid, SIGTERM)` 走的是
   `TerminateProcess`，根本不会进 Python 的 handler，所以冒烟里只能桩验调用顺序。

## 12. 已知局限

- 归因依赖 `crypto/logs/` 可写。目录被清（例如发版时整包替换且 logs 不在持久卷）会把
  一次内存自愈误判成 `first_run`，代价是"该起没起"，会发信求救，不会静默。
- `cold_start` 无法区分"人工重启"和"机器重启后自启"，两者处置相同（按时间窗），不影响结果。
- 熔断计数是"自愈类启动次数"，不等于"崩溃次数"：面板优雅重启现在归 `cold_start`，
  **不占熔断额度** —— 这是故意的：人在反复手动重启一个坏环境，不该由机器拦着人不让起。
- SIGTERM 只覆盖"优雅停止"：`kill -9`、面板强杀、机器断电仍然没有标记，仍归 `abnormal_death`。
  处置本来就该一样（按时间窗接回），只是标签保守一点。
- 若改用自带 SIGTERM 处理器的 WSGI 服务器（或它在 `import crypto.app` 之后才装），
  我们的处理器会被顶掉，面板重启回落到 `abnormal_death` 标签（处置不变）。
  确认方法就是看启动日志里有没有「已捕获 SIGTERM」那一行。
- 未做：页面上显示自动拉起倒计时（需要在只读状态接口里塞计划时间并前端逐秒渲染，收益低于噪声），
  以及按币种/按账户的差异化自愈策略。
