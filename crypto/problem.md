## 一、项目内自监控 + 超内存自动重启（直接让 AI 加到代码里）

**完全可以在项目里写，不需要你人工盯。** 原理：开一个后台线程，每隔几分钟检查一次进程自身内存，超过阈值就优雅退出，supervisord 会自动把它拉起来（内存重置回 271MB）。

把下面这段代码直接发给写项目的 AI，让它加到 `app.py` 里：

```python
import threading
import os
import time
import logging

def memory_monitor(threshold_mb=800, check_interval=300):
    """
    后台内存监控线程，超过阈值自动退出进程，由 supervisord 自动重启。
    threshold_mb: 内存阈值，单位MB，建议设为 800（你机器2G，留余量）
    check_interval: 检查间隔，单位秒，默认5分钟
    """
    def _monitor():
        pid = os.getpid()
        while True:
            try:
                # 读取自身内存占用（RSS）
                with open(f'/proc/{pid}/status') as f:
                    for line in f:
                        if line.startswith('VmRSS:'):
                            rss_kb = int(line.split()[1])
                            rss_mb = rss_kb / 1024
                            break
                
                logging.warning(f"[内存监控] 当前占用: {rss_mb:.1f}MB / 阈值: {threshold_mb}MB")
                
                if rss_mb > threshold_mb:
                    logging.critical(f"[内存监控] 内存超限 {rss_mb:.1f}MB > {threshold_mb}MB，准备退出重启")
                    # 这里可以加优雅退出逻辑：关闭websocket、保存状态等
                    os._exit(1)  # 强制退出，supervisord会自动重启
                    
            except Exception as e:
                logging.error(f"[内存监控] 检查失败: {e}")
            
            time.sleep(check_interval)
    
    t = threading.Thread(target=_monitor, daemon=True)
    t.start()
    logging.info("[内存监控] 已启动")

# 在 app.py 启动时调用（在 main 函数最开头）
memory_monitor(threshold_mb=800, check_interval=300)
```

**关键点：**
- 阈值设 **800MB**（你机器2G，项目超过800MB就说明泄漏已经比较严重了，趁早重启）
- 每 **5 分钟**检查一次，完全不耗性能
- 退出后 supervisord 会自动重启，整个过程你无感知
- 如果有 WebSocket 连接或需要保存状态，在 `os._exit(1)` 之前加清理逻辑

## 二、全面崩溃监控方案（进程挂了 + 系统异常 + 告警推送）

光靠项目自监控不够，如果项目直接崩了（代码异常、段错误等），监控线程也跟着死了。需要**系统层面的独立监控**。

### 方案：Shell 脚本 + Cron + 企业微信告警

写一个监控脚本，每分钟检查一次：
1. 项目进程是否存活
2. 内存是否超限
3. 磁盘是否满了
4. 系统负载是否过高
5. 有问题就推送到企业微信/钉钉

先确认你的 supervisord 配置里项目有没有开 `autorestart=true`：

```bash
cat /etc/supervisor/conf.d/*.conf
```

把输出贴给我，我帮你确认自动重启是否开启，以及帮你写完整的监控脚本。

### 监控脚本大致逻辑（先给你看思路）

```bash
#!/bin/bash
# 每分钟由 cron 调用

# 1. 检查进程是否存活
if ! pgrep -f "cryptoTrade/app.py" > /dev/null; then
    # 进程没了，尝试重启 + 告警
    supervisorctl restart your_project_name
    send_alert "量化交易进程崩溃，已自动重启"
fi

# 2. 检查内存使用率
MEM_USED=$(free | awk '/Mem:/{printf "%.0f", $3/$2*100}')
if [ "$MEM_USED" -gt 90 ]; then
    send_alert "内存使用率 ${MEM_USED}%，即将OOM"
fi

# 3. 检查磁盘
DISK_USED=$(df / | awk 'NR==2{print $5}' | tr -d '%')
if [ "$DISK_USED" -gt 90 ]; then
    send_alert "磁盘使用率 ${DISK_USED}%"
fi
```

## 三、高可用：一台宕机自动切另一台？

这个问题要慎重，**量化交易的高可用和普通网站不一样，不能简单做负载均衡。**

### 为什么不能直接负载均衡

如果两台服务器同时跑同一个量化策略，会出现：
- **重复下单**：两台都检测到信号，都下单，仓位翻倍
- **状态不一致**：A 机下了单，B 机不知道，可能重复下或错误平仓
- **数据不同步**：持仓、订单状态两边对不上

**量化交易应该用"主备模式"（一主一备），不是负载均衡：**

```
正常情况：  主服务器（运行交易）  ←→  备服务器（待命，不交易）
                ↓ 主服务器宕机
自动切换：  主服务器（宕机）      →  备服务器（接管，开始交易）
```

### 实现方案（按复杂度排序）

#### 方案 A：轻量级主备（推荐，成本低）

- 备服务器上跑一个"监控切换脚本"，每隔 10 秒 ping 主服务器
- 连续 3 次 ping 不通，认为主服务器宕机，备服务器自动启动交易程序
- 主服务器恢复后，手动切回（避免脑裂）

**优点**：实现简单，两台低配服务器就行
**缺点**：切换有 30 秒延迟，切换期间可能错过交易信号

#### 方案 B：交易所层面兜底（最实用）

其实量化交易最关键的不是"程序永远在线"，而是**"程序挂了的时候，仓位不会失控"**。比起搞主备，更重要的是：

1. **止损单挂在交易所服务器上**：用条件单/止损单，就算你程序全挂了，交易所也会自动止损
2. **策略无状态化**：每次启动时从交易所 API 拉取当前持仓和订单，不依赖本地状态
3. **关键操作加幂等性**：重启后不会重复下单

#### 方案 C：专业高可用（成本高，不推荐个人用）

- 共享存储 + 浮动 IP + 心跳检测（Keepalived）
- 两台服务器同一局域网，共享状态
- 月成本至少几百块，个人量化没必要

### 我的建议

| 你的情况 | 推荐方案 |
|---|---|
| 只有1台服务器，预算有限 | **先做方案一（自监控重启）+ 方案二（告警）+ 交易所止损单兜底**，这三个加起来能解决 95% 的问题 |
| 有2台服务器，想做主备 | **方案 A 轻量级主备**，我可以帮你写切换脚本 |
| 资金量大，不能断 | 方案 B + 方案 A 组合，同时考虑用云服务器的弹性伸缩 |

## 四、量化交易特有的稳定性建议

既然是跑量化，除了上面说的，还有几点特别重要：

1. **程序启动时必须从交易所同步状态**：不要信任本地保存的持仓/订单，启动时先调 API 拉取最新状态，防止重启后状态错乱
2. **下单前检查仓位**：每次下单前先查当前持仓，避免重复下单
3. **用交易所的条件单做止损**：不要只靠程序里的止损逻辑，程序挂了就没了
4. **日志要记录关键操作**：下单、平仓、报错都要记日志，出问题能回溯
5. **网络重连机制**：WebSocket 断开后要自动重连，不能直接退出
