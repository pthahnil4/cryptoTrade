# 定时任务系统详细分析

## 一、系统架构概览

定时任务系统位于 `crypto/task/` 目录下，是一套面向 OKX 交易所永续合约的**自动化量化交易框架**。系统由以下核心模块组成：

```
crypto/task/
├── scheduler.py                      # 通用任务调度器（APScheduler 封装）
├── crypto_analysis_batch.py          # 批量行情分析引擎（Pro3+ 指标计算）
├── trend_range_trader.py             # 实盘交易调度器（趋势跟踪仓 + 区间波动仓）
├── getBOLL.py                        # BOLL 指标实时计算模块
├── __init__.py                       # 模块初始化
├── config/
│   ├── config_trend_range.json       # 实盘交易配置文件（币种、周期、仓位参数）
│   └── email_config.py               # 邮件 SMTP 配置
├── notification/
│   ├── email_tool.py                 # 统一邮箱工具类（发送/模板/重试）
│   └── message_notifier.py           # 消息通知编排器（冷却期 + 重试）
└── utils/
    ├── trade_executor.py             # 交易执行器（TWAP/追逐限价/减仓/移动止损）
    ├── strategy_order_manager.py     # 策略委托生命周期管理
    └── position_manager.py           # 资金仓位管理（阶梯式/TWAP参数/止盈计算）
```

## 二、各模块功能详解

### 2.1 通用任务调度器 — `scheduler.py`

**文件定位**：基于 APScheduler 的轻量级调度框架封装，提供全局单例 `task_scheduler`。

#### 核心类：`TaskScheduler`

| 属性/方法 | 说明 |
|-----------|------|
| `_scheduler` | `BackgroundScheduler` 实例，后台线程运行 |
| `_started` | 启动状态标志（幂等控制） |
| `_job_registry` | 已注册任务的元信息字典 |

**调度器默认配置**（`job_defaults`）：

| 参数 | 值 | 含义 |
|------|----|------|
| `coalesce` | `True` | 合并错过的执行（如果调度器停机期间错过了多次触发，只执行一次） |
| `max_instances` | `1` | 同一任务最多 1 个实例并发运行 |
| `misfire_grace_time` | `60` | 错过执行的容忍时间为 60 秒 |

**支持的三种触发器**：

1. **`interval`（间隔触发）**：按固定时间间隔执行
   - 参数示例：`seconds=60`, `minutes=5`, `hours=1`
   - 使用 `IntervalTrigger` 实现
   
2. **`cron`（定时触发）**：按 cron 表达式执行
   - 参数示例：`hour=8`, `minute=0`, `day_of_week='mon-fri'`
   - 使用 `CronTrigger` 实现
   
3. **`date`（一次性触发）**：在指定时间点执行一次
   - 参数示例：`run_date='2025-01-01 08:00:00'`
   - 使用 `DateTrigger` 实现

**关键方法**：

- `register_job(func, trigger, job_id, ...)` — 注册任务，自动创建触发器实例并记录元信息
- `remove_job(job_id)` — 移除任务
- `pause_job(job_id)` / `resume_job(job_id)` — 暂停/恢复任务
- `get_all_jobs()` — 获取所有任务状态（含下次执行时间）
- `get_status()` — 获取调度器整体状态

**全局单例**：`task_scheduler = TaskScheduler()`，供整个项目共享使用。

**默认示例任务**：`register_default_jobs()` 注册一个每 10 分钟执行的示例任务 `sample_task`。

### 2.2 批量行情分析引擎 — `crypto_analysis_batch.py`

**文件定位**：批量遍历数据库中所有加密货币的 5m~1W 周期，调用 OKX 行情 API 计算 Pro3+ 指标，并写回数据库 `okx_crypto_analysis` 表。

#### 核心类：`CryptoAnalysisBatch`

**时间周期配置**：
```python
self.time_periods = ['5m', '15m', '1H', '4H', '1D', '1W']
```

**新币种过滤规则**：
- 新币种列表：`['TRUMP-USDT-SWAP']`
- 跳过周期：`['1W']`（新币种跳过周线分析，因上线时间短，历史数据不足）

#### Pro3+ 指标计算流程

**Step 1：ADX 指标计算**（`calculate_adx` 函数，周期=14）
- 计算 True Range (TR)：取 `H-L`、`|H-prev_C|`、`|L-prev_C|` 三者最大值
- 计算 +DM / -DM（方向运动）
- 使用 EWM（alpha=1/14）平滑得到 ATR、+DM_smooth、-DM_smooth
- 计算 +DI、-DI、DX，最终 EWM 平滑得到 ADX

**Step 2：ATR 比值计算**（`calculate_atr_ratio` 函数，周期=20）
- ATR 使用 EWM(span=14) 计算
- ATR_MA 使用 Rolling(window=20) 计算 ATR 的移动平均
- `ATR_ratio = 当前ATR / MA(ATR, 20)`

**Step 3：自适应权重计算**（`get_adaptive_smooth_weight_plus` 函数）

输入参数：
- `adx_value`：当前 ADX 值
- `atr_ratio`：ATR / MA(ATR) 比值
- `base_weight`：基础权重，默认 0.675
- `adx_divisor`：ADX 缩放因子，默认 120.0

权重调整规则：
| ATR Ratio 范围 | ATR 调整值 | 含义 |
|----------------|-----------|------|
| > 1.2 | -0.06 | 高波动，降低权重，更敏感 |
| > 1.0 | -0.03 | 偏高波动 |
| < 0.8 | +0.04 | 低波动，提高权重，更保守 |
| < 0.9 | +0.02 | 偏低波动 |
| 0.9~1.0 | 0.0 | 正常波动 |

最终权重：`hist_weight = base_weight + adx_adjust + atr_adjust`，限制在 `[0.65, 1.0]` 范围内。

**Step 4：MACD 计算**
- EMA12 = close.ewm(span=12)
- EMA26 = close.ewm(span=26)
- MACD Line = EMA12 - EMA26
- Signal Line = MACD.ewm(span=9)
- Histogram = 2 × (MACD - Signal)

**Step 5：自适应平滑 MACD**
- 对每个 bar，使用 ADX+ATR 自适应权重平滑 Histogram：
  ```
  smoothed[i] = smoothed[i-1] × hist_weight + histogram[i] × curr_weight
  ```

**Step 6：交易信号生成**

信号状态机（`justice_flag` + `modify_flag`）：

| 状态 | 条件 | 动作 |
|------|------|------|
| `smoothed_histogram` | `histogram - smoothed > 0` 且前一根 MACD > 0 | `modify_flag = "rise"` |
| `smoothed_histogram` | `histogram - smoothed > 0` 且前一根 MACD < 0 | 切换到 `histogram` 状态，等待 `waitRise` |
| `smoothed_histogram` | `histogram - smoothed ≤ 0` 且前一根 MACD < 0 | `modify_flag = "fall"` |
| `histogram` (waitRise) | `histogram > 0` | `modify_flag = "rise"`，回到 `smoothed_histogram` |
| `histogram` (waitFall) | `histogram < 0` | `modify_flag = "fall"`，回到 `smoothed_histogram` |

**开多信号**：`modify_flag` 从 `"fall"` 变为 `"rise"`
**开空信号**：`modify_flag` 从 `"rise"` 变为 `"fall"`

**交易价格确定**：
- 如果在 `waitRise`/`waitFall` 状态下触发，使用 `histogram_zero` 价格
- 否则使用 `hist_smooth_diff_zero` 价格
- 如果计算价格超出当前 K 线高低范围，回退为开盘价

**资金管理**：
- 基础资金：100 USDT
- 杠杆倍数：10 倍
- 三种资金曲线：复投（compound）、定投（DCA）、混投（mix，基于 1.6 对数阶梯加仓）

**Step 7：统计指标计算**
- 胜率 = 盈利次数 / 总交易次数 × 100%
- 复利收益 = 最终资金 / 初始资金
- 盈亏比 = 总盈利 / |总亏损|
- 信号强度 = min(100, 胜率 × 盈亏比)
- ATR% = ATR / 当前价格 × 100%

#### 数据库更新逻辑

| 时间周期 | 更新字段 | 特殊处理 |
|----------|---------|---------|
| `5m` | `dir_5m`, `px_5m`, `time_5m` | - |
| `15m` | `dir_15m`, `px_15m`, `time_15m` | - |
| `1H` | `dir_1h`, `px_1h`, `time_1h`, `current_profit` | 唯一更新 `current_profit` 的周期 |
| `4H` | `dir_4h`, `px_4h`, `time_4h` | - |
| `1D` | `dir_1d`, `px_1d`, `time_1d` | - |
| `1W` | `dir_1w`, `px_1w`, `time_1w` | - |

所有周期都会同时更新 `last_px`、`signal_strength` 和 `update_time`。

#### 双周期分析 — `calculate_dual_period`

调用 `crypto/strategy/pro3_dualtimeframe.py` 的真双周期逻辑：

1. 导入 `pro3_singletimeframe` 和 `pro3_dualtimeframe` 模块
2. 抑制所有输出（`FAST_MODE=True`, 各 `PRINT_*=0`）
3. 调用 `_dual.get_latest_data_dual(instId, short_bar, long_bar)` 获取分析结果
4. 返回结果包含额外字段 `long_direction`（长周期方向）
5. 失败时自动回退到独立双周期分析（分别计算短/长周期再合并）

#### 网络故障降级

当 OKX API 网络请求失败时，`_generate_mock_analysis_result` 生成模拟数据：
- 价格基于 BTC/ETH/其他币种的基础价格 ±5% 波动
- 方向随机选择 long/short
- 胜率在 45-65% 之间随机
- 交易时间对齐到当前 K 线周期起始时间

#### 数据库连接管理

使用连接池模式（`database.db_config.get_pooled_connection`）：
- 连接获取超时：10 秒
- 连接保活检查：`ensure_connection_alive`
- 连接归还：`return_pooled_connection`
- 异常时自动重连或关闭

### 2.3 实盘交易调度器 — `trend_range_trader.py`

**文件定位**：主账号实盘交易调度器，实现"双周期趋势 + BOLL 波动仓"的三周期策略。

#### 核心类：`TrendRangeTrader`

##### 初始化流程

1. **配置加载**：从 `config_trend_range.json` 读取交易配置
2. **API 验证**：验证 OKX API 配置必须为实盘环境（`flag=0`）
3. **组件初始化**：
   - `TradeExecutor`：交易执行器
   - `StrategyOrderManager`：策略委托管理器
   - `MessageNotifier`：消息通知器
4. **邮件连接测试**：启动时自动测试 SMTP 连接
5. **信号处理器注册**：`SIGINT` / `SIGTERM` → `stop()`

##### 交易周期配置

```python
period_pairs = {
    '5m': '1H',    # 5分钟 → 1小时
    '15m': '4H',   # 15分钟 → 4小时
    '1H': '1D'     # 1小时 → 1天
}
```

##### 执行频率配置

| 短周期 | 检查间隔 | 说明 |
|--------|---------|------|
| `5m` | 60 秒 | 每 1 分钟检查一次 |
| `15m` | 180 秒 | 每 3 分钟检查一次 |
| `1H` | 60 秒 | 每 1 分钟检查一次 |

##### 四场景策略分类

本策略为**纯多头策略**（只做多或空仓，不做空），由短周期（1H）和长周期（1D）方向组合决定四种场景：

**场景 1：1H rise + 1D rise（趋势一致做多）**
- 场景标识：`aligned_long`
- 底仓：配置值（`base_reserve`，默认 0.1 张）
- 波动仓：BOLL 下轨挂买单开多，上轨挂卖单平多
- 最大持仓：`target_position`

**场景 2：1H rise + 1D fall（信号冲突，短多长空）**
- 场景标识：`conflict_short_long`
- 底仓：极小值 0.2 张（降低风险敞口）
- 波动仓：正常 BOLL 操作
- 最大持仓：`target_position`

**场景 3：1H fall + 1D rise（信号冲突，短空长多）**
- 场景标识：`conflict_long_short`
- 操作：撤销所有挂单 + 强制平仓全仓持仓
- 不开新仓

**场景 4：1H fall + 1D fall（趋势一致做空）**
- 场景标识：`aligned_short`
- 操作：撤销所有挂单 + 强制平仓全仓持仓
- 不开新仓（纯多头策略不做空）

##### 核心交易逻辑 — `_execute_trend_strategy`

**阶段 0：反向持仓检测**
- 如果当前持仓为空头（`< -0.01`），与多头目标矛盾
- 执行强制平空（`execute_reduce_only_order`）
- 发送平仓通知

**阶段 A：底仓管理**
- **触发条件**：信号已确认（`is_signal_confirmed=True`）且当前空仓（`|position| < 0.01`）
- **操作**：市价买入 `base_reserve` 张
- **限制**：仅在空仓时执行一次，已有持仓不补底仓
- **信号未确认**：跳过底仓开仓，仅限价挂单

**阶段 B：波动仓位管理（BOLL 区间挂单）**

BOLL 数据获取（`getBOLL.py` 模块）：
- 使用标记价格 K 线（`get_mark_price_candlesticks`），失败时回退到普通 K 线
- 默认参数：周期 20，标准差倍数 2.0
- 数据量：100 根 K 线
- 输出：上轨（UB）、中轨（MB）、下轨（LB）

**买单维护**（BOLL 下轨挂单开多/加仓）：
- 目标价格 = BOLL 下轨
- 挂单数量 = min(`fluctuation_lots`, `target_position - current_position`)
- 如果当前持仓已达上限，撤销所有买单
- 使用 `_maintain_limit_order` 维护挂单（无则挂、有则检查是否需要改单）

**卖单维护**（BOLL 上轨挂单平多）：
- 目标价格 = BOLL 上轨
- 挂单数量 = min(`fluctuation_lots`, `current_position - base_reserve`)
- 只有超出底仓部分才挂卖单
- 如果无需卖出，撤销所有卖单

##### 限价挂单维护逻辑 — `_maintain_limit_order`

1. 查询当前未成交的限价单（筛选当前交易模式 + 同方向）
2. **无挂单**：直接挂单
3. **有挂单**：检查是否需要修改
   - 价格偏差 > 0.2% → 改单（`amend_order`）
   - 数量变化 > 0.01 → 改单
   - 否则保持不变

##### 人工干预机制

- **配置文件级**：在 JSON 配置中设置 `manual_direction`（`long`/`short`/`auto`）
- **运行时级**：通过 `set_manual_override` 动态设置
- **优先级**：配置文件级 > 运行时级 > 策略信号
- **效果**：人工指定时，短周期和长周期方向都强制设为指定值，且信号视为已确认

##### 全仓/逐仓隔离保护

- 从配置读取 `trading_mode`（`cross_only` / `isolated_only`）
- 所有交易操作仅针对目标模式持仓
- 强制平仓时只操作全仓持仓，逐仓持仓完全隔离不受影响

##### BOLL 触达通知

- 检测当前 K 线高低价是否触及 BOLL 上下轨
- 使用周期内去重机制（`_get_current_period_key`），同一 K 线周期内只通知一次
- 去重 key 格式：`{币种}_{周期}_{周期key}_{触轨类型}`

##### 主循环 — `start_real_scheduler`

```
while running:
    1. 检查是否到达最小执行间隔
    2. 如果是，执行 run_real_trading_batch()
    3. 等待 10 秒
    4. 异常时等待 30 秒
```

##### 批量执行流程 — `run_real_trading_batch`

1. 运行计数器 +1
2. 从配置文件获取所有交易币种和周期列表
3. 更新所有策略委托单状态（`order_manager.update_order_status()`）
4. 遍历每个币种-周期对：
   - 读取配置参数（目标持仓、波动手数、底仓、BOLL周期、人工方向）
   - 更新人工方向配置
   - 执行 `run_real_trading_for_currency_period`
   - 打印持仓明细报告
5. 支持 `stop_event` 中断

### 2.4 BOLL 指标模块 — `getBOLL.py`

**功能**：实时获取 K 线数据并计算 Bollinger Bands 指标。

**K 线获取逻辑**（`_fetch_candles`）：
1. 优先使用标记价格 K 线（`get_mark_price_candlesticks`）
2. 失败时回退到普通 K 线（`get_candlesticks`）
3. 支持分页获取（最多 5 次额外请求）
4. 数据预处理：反序、时间戳转 UTC+8、float 类型转换

**BOLL 计算**（`_compute_boll`）：
- 中轨 (MB) = close.rolling(20).mean()
- 标准差 (STD) = close.rolling(20).std()
- 上轨 (UB) = MB + 2.0 × STD
- 下轨 (LB) = MB - 2.0 × STD

**趋势检测**（`_detect_trend`）：
- 基于中轨（MB）最近 10 根 K 线的斜率
- 斜率 > 0 → "up"
- 斜率 < 0 → "down"
- 否则 → "flat"

**返回数据结构**：
```python
{
    "analysis": {"trend": "up/down/flat"},
    "bollinger_bands": {"upper": float, "lower": float, "mid": float},
    "basic_info": {"current_price": float, "instId": str, "bar": str, "timestamp": str},
    "current_candle": {"high": float, "low": float, "open": float, "close": float}
}
```

### 2.5 交易执行器 — `utils/trade_executor.py`

**文件定位**：封装 OKX API 的交易操作，支持多种委托类型。

#### 核心类：`TradeExecutor`

**API 客户端初始化**：
- `MarketData.MarketAPI`：行情数据
- `Trade.TradeAPI`：交易操作
- `PublicData.PublicAPI`：公共数据
- `Account.AccountAPI`：账户信息

**防重机制**：
- 策略状态文件：`trade_state.json`（持久化）
- 签名计算：`MD5(inst_id|side|total_amount|px_limit|timestamp)`
- 阻止条件：相同签名 + 状态为 creating/live/partially_filled，或 order_id 在 pending 集合中

##### 支持的委托类型

**1. 统一交易接口 — `execute_trade`**
- 支持限价单（`limit`）和市价单（`market`）
- 支持全仓（`cross`）和逐仓（`isolated`）
- 可选 `posSide`（long/short/net）

**2. 时间加权委托 (TWAP) — `execute_twap_order`**
- 参考 demo37 实现
- 参数：总量、间隔、单笔量、限制价
- 交易模式：同向 → 全仓，不同向 → 逐仓
- 智能 posSide 检测（兼容 Hedge 模式）
- 余额不足时发出警告但继续尝试（TWAP 分批执行）
- 失败时降级为普通限价单（`_fallback_to_limit_order`）

**3. 减仓/平仓委托 — `execute_reduce_only_order`**
- 参考 demo27 实现
- `reduceOnly=True`，不占用额外保证金
- 自动检测交易模式和持仓方向
- 自动匹配 posSide（sell 对应 long，buy 对应 short）

**4. 追逐限价委托 — `execute_chase_limit_order`**
- 参考 demo34 实现
- 限制价：买入 +0.2%，卖出 -0.2%
- 余额不足时自动减仓释放资金
- 不支持时降级为限价单
- 3 次网络重试机制
- 自动清理错误持仓（`_auto_cleanup_for_balance`）

**5. 移动止盈止损 — `create_trailing_stop_order`**
- 参考 demo36 实现
- 使用逐仓模式
- 可配置回调比例和激活价格

**6. 平仓 — `close_position`**
- 使用 `close_positions` API
- 全仓模式

##### 持仓管理

- `get_positions`：获取有效持仓（过滤 pos=0）
- `get_all_positions_by_mode`：按模式分类（cross/isolated）
- `get_position_trading_mode`：获取当前持仓的交易模式
- `get_account_balance`：获取 USDT 余额详情
- `check_pending_orders_before_trade`：下单前防重检查（普通委托 + 策略委托）

### 2.6 策略委托管理器 — `utils/strategy_order_manager.py`

**文件定位**：管理策略委托单的生命周期，根据信号类型选择委托策略。

#### 信号类型枚举

| 类型 | 值 | 含义 |
|------|----|------|
| `UNCERTAIN` | `uncertain` | 不确定信号（当前周期） → TWAP 委托 |
| `CONFIRMED` | `confirmed` | 确定信号（上周期） → 追逐限价委托 |
| `DISAPPEARED` | `disappeared` | 信号消失 → 撤销委托 |

#### 信号处理逻辑

**不确定信号处理**（`_handle_uncertain_signal`）：
1. 已有同向 TWAP 委托 → 保持
2. 已有反向委托 → 撤销
3. 方向反转（持仓与目标方向相反）→ 先 TWAP 平仓，等平仓完成后再开反向仓
4. 同方向调整 → 计算差值，创建 TWAP 委托
5. 调整量 < 0.2 张 → 跳过（已达目标）

**确定信号处理**（`_handle_confirmed_signal`）：
1. 如果有 TWAP 委托，先撤销并获取剩余数量
2. 创建追逐限价委托（快速成交）
3. 交易数量 < 0.2 张 → 跳过

**信号消失处理**（`_handle_disappeared_signal`）：
- TWAP 委托 → 撤销
- 追逐限价委托 → 保留（已接近成交，不轻易撤销）

#### 周期转换检测

`check_period_transition`：检查 TWAP 委托是否跨越了 K 线周期边界。

`transition_to_chase_limit`：将 TWAP 委托转换为追逐限价委托
- 获取 TWAP 执行进度（已成交量/剩余量）
- 撤销 TWAP
- 用剩余数量创建追逐限价委托

#### 委托单状态更新

`update_order_status`：遍历所有活动委托，查询最新状态，已完成/已撤销/失败的从活动列表移除。

### 2.7 资金仓位管理器 — `utils/position_manager.py`

**文件定位**：阶梯式资金管理、仓位计算、止盈级别计算。

#### 资金管理

**阶梯式本金计算**（`calculate_available_capital`）：
- 盈利时：交易本金 = 初始本金 + 盈利 × 分润比例（默认 40%）
- 亏损或持平：交易本金 = 初始本金

#### 仓位计算

**分层仓位比例**（`calculate_contract_amount`）：

| 短周期 | 同向比例 | 反向比例 |
|--------|---------|---------|
| `1H` (1H/1D) | 100% | 50% |
| `15m` (15m/4H) | 50% | 25% |
| `5m` (5m/1H) | 25% | 12.5% |

计算公式：
```
目标价值 = 可用本金 × 仓位比例
目标张数 = 目标价值 / 当前价格
调整量 = 目标张数 - 当前持仓
```

最小交易张数：0.2 张。

#### TWAP 参数配置

| 短周期 | 间隔 | 单笔比例 | 总执行时间 | 对应长周期 |
|--------|------|---------|-----------|-----------|
| `1H` | 300 秒 | 10% | 50 分钟 | `1D` |
| `15m` | 60 秒 | 10% | 10 分钟 | `4H` |
| `5m` | 60 秒 | 20% | 5 分钟 | `1H` |

单笔最小张数：0.2 张。

#### 止盈级别计算

**同向止盈**（2ATR、4ATR、6ATR）：

| 级别 | ATR 倍数 | 减仓比例 | 备注 |
|------|---------|---------|------|
| 1 | 2 ATR | 30% | - |
| 2 | 4 ATR | 40% | - |
| 3 | 6 ATR | 30% | 最后一级使用移动止盈 |

**反向止盈**（1ATR、2ATR、3ATR）：

| 级别 | ATR 倍数 | 减仓比例 | 备注 |
|------|---------|---------|------|
| 1 | 1 ATR | 30% | - |
| 2 | 2 ATR | 40% | - |
| 3 | 3 ATR | 30% | 最后一级使用移动止盈 |

## 六、调度器工作原理

### 6.1 通用调度器（scheduler.py）

基于 APScheduler 的 `BackgroundScheduler`，在后台线程中运行：

```
应用启动
    ↓
task_scheduler.start()
    ↓
BackgroundScheduler 在后台线程轮询触发器
    ↓
触发器匹配 → 执行注册的函数
    ↓
coalesce=True → 合并错过的执行
max_instances=1 → 防止并发
misfire_grace_time=60 → 60秒内可补执行
```

### 6.2 实盘调度器（trend_range_trader.py）

自定义主循环（不依赖 APScheduler），独立运行：

```
main()
    ↓
TrendRangeTrader.__init__()
    ├─ 加载配置
    ├─ 初始化 API
    ├─ 初始化通知器
    └─ 注册信号处理器
    ↓
start_real_scheduler()
    ↓
while running and not stop_event:
    ├─ 检查最小间隔 (60秒)
    ├─ run_real_trading_batch()
    │   ├─ 遍历所有币种-周期
    │   ├─ 分析 + 交易
    │   └─ 打印持仓报告
    ├─ stop_event.wait(10) — 等待 10 秒
    └─ 异常时 wait(30) — 等待 30 秒
    ↓
stop() → running=False, stop_event.set()
```

**停止机制**：
- `SIGINT`（Ctrl+C）或 `SIGTERM` → `_signal_handler` → `stop()`
- `stop_event` 线程事件 → 主循环优雅退出
- `KeyboardInterrupt` → 直接退出循环

## 七、关键业务规则总结

1. **纯多头策略**：只做多或空仓，绝不做空
2. **双周期确认**：短周期（1H）+ 长周期（1D）方向一致时正常交易
3. **信号确认期**：底仓市价开仓需信号确认，限价挂单不受限制
4. **全仓隔离保护**：只操作全仓持仓，逐仓持仓完全不受影响
5. **BOLL 挂单**：波动仓位在 5m BOLL 下轨买入、上轨卖出
6. **底仓保留**：卖出时保留底仓（`base_reserve`），只卖超出部分
7. **人工干预优先**：人工指定方向覆盖策略信号
8. **冷却期通知**：同一币种 30 分钟内最多发 1 封邮件
9. **防重下单**：MD5 签名 + 状态检查，防止重复委托
10. **降级策略**：TWAP/追逐限价不支持时自动降级为普通限价单
