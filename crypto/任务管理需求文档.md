# 任务卡「任务管理（任务树）」需求文档

> 版本：v1.0（Q1–Q16 全部确认 · 定稿）
> 日期：2026-09-16
> 模块：任务计划（`/plan`）· 任务卡
> 关联文档：《任务计划系统设计文档（长期主义 v1.1）》《任务计划功能模块说明》
> 预计落地文件：`crypto/plan_routes.py`、`plan_repo.py`、`models.py`、`db_schema.sql`、`static/js/task_plan.js`、`templates/task_plan.html`

---

## 1. 背景与现状问题

任务卡目前存在 **3 套互不关联的"任务管理"结构 + 1 套打卡记录**：

| 结构 | 现状 | 问题 |
|------|------|------|
| 任务目标 `goal` | 一段自由文本 | 不可执行、不可追踪 |
| 目标拆解 `milestones` | 平铺勾选清单 `{content, done}` | 无层级、与打卡无关 |
| 待办清单 `todos` | 平铺勾选清单 `{content, done}` | 与目标拆解职责重叠、与打卡无关 |
| 100 格打卡 `slots` | 每次打卡 = 内容 + 时长 | **不知道这次打卡在推进哪个任务**，记录与任务脱节 |

**核心缺陷**：打卡记录与任务结构零关联——做完一件事打卡后，看不出它推进了哪个任务；也没有"预估工作量 vs 实际投入"的对比。

---

## 2. 需求目标

> 用**一棵可无限拆分的任务树**统一"目标拆解 + 待办清单"两套结构；
> 每次打卡**关联至少一个任务节点**（可多选，选择时机在打卡结束，见 Q11）；
> 各任务独立标记"进行中 / 已完成"；
> 卡片提供**双进度条**：任务进度（按叶子任务预估工作量加权）+ 工时进度（格数/100）。

### 2.1 已确认核心决策（Q1–Q16）

| # | 决策项 | 确认结果 |
|---|--------|----------|
| Q1 | 层级深度 | **不限层级**，UI 折叠展开 |
| Q2 | 父任务预估 | 父任务只是任务名（纯容器）；**所有统计只计算末端叶子节点的工作量，逐级累加**；父任务预估 = Σ 叶子工作量（自动，只读） |
| Q3 | 叶子预估填写 | **必须填写**（工作量 = 时长口径），用于与实际打卡数据做对比 |
| Q4 | 打卡关联 | **必须关联任务**（最终口径：打卡结束时引导必选 ≥1；开始时可不选，见 Q11）；**一条打卡可关联多个任务**（多对多） |
| Q5 | 完成标记 | **只能通过打卡标记完成**（树上不可勾选）；**已完成的任务不能再打卡** |
| Q6 | 父任务完成 | 子任务全部完成 → 父任务**自动完成**（逐级上卷） |
| Q7 | 删除打卡 | 删除"完成依据"打卡 → 对应任务**自动回退"进行中"**（含已上卷的父任务） |
| Q8 | 进度条 | **双进度条**：任务加权进度为主 + 工时进度（格数/100）为辅，标注清楚"任务进度 / 工时进度" |
| Q9 | 交易卡 | **同样启用任务树与打卡关联**；任务范围不限于交易执行，还包括量化研究、测试、开发、资源获取与解读等 |
| Q10 | 旧数据迁移 | milestones + todos **自动迁移**为任务树顶层节点，旧列归档一版；**进行中的任务卡允许修改节点、名称、时长等所有内容**（工作量就是时长） |
| Q11 | 任务树位置 / 选任务时机 | 概览 Tab 与独立「🌳 任务」Tab **均显示**任务树；**打卡开始时无需选任务，打卡结束后再选择关联任务**（开始时无法预测接下来 60 分钟能完成哪些任务） |
| Q12 | 排序交互 | 一期：上移 / 下移按钮；拖拽排序二期 |
| Q13 | 多任务打卡实际时长 | **不做分摊**：每个关联任务按打卡时长**全额**计入（1h 打卡关联 A、B → A、B 各 +1h）；预估与实际相互独立（预估 2h 可能 1h 做完，也可能 4h 才做完） |
| Q14 | 任务状态标记 | 每条打卡内**每个任务独立标记**（进行中 / 已完成） |
| Q15 | 取消完成入口 | **树上提供"取消完成"**：点击后自动把完成依据打卡中该任务改回"进行中"，上卷父任务同步回退 |
| Q16 | 满 100 格与任务树未完成 | **维持现状**：满 100 格自动结算通关；任务树未完成则随卡结束、保留只读可查看（不做格子溢出机制） |

### 2.2 用户示例（个人博客网站）

```
个人博客网站（主任务/根节点，纯容器）
├── 任务1：寻找建站工具、开源项目        （预估 4h）
├── 任务2：确定目标网站，了解网站结构和内容（预估 5h）
└── 任务3：部署上线                      （纯容器，= Σ 子任务 6h）
    ├── 域名注册            （1h）
    ├── 域名解析            （0.5h）
    ├── 项目打包            （1h）
    ├── 宝塔面板部署配置     （2h）
    └── 网站备案            （1.5h）
```

完成任务 1 + 2 → 任务进度 = (4+5) ÷ 15 = **60%**

> 口径说明：打卡时长与任务工作量是**两套独立度量**，双进度条天然不同步，这是预期行为。
> 任务节点的"实际时长"按每条关联打卡**全额**计入（Q13），多任务关联时各节点实际之和可大于打卡总时长，属预期口径；
> 因此"100 小时打卡可能完成合计 200 小时工作量的任务"。

## 3. 核心概念与数据模型

### 3.1 任务节点 TaskNode（新增）

| 字段 | 类型 | 说明 |
|------|------|------|
| id | string | 唯一标识，如 `task_a1b2c3` |
| title | string | 任务名称（父任务只是名字） |
| estimated_minutes | int | 预估工作量（分钟存储、界面按小时输入）；**仅叶子填写、必填**；父节点 = Σ 叶子（自动计算、只读） |
| status | enum | `todo` 未开始 / `doing` 进行中 / `done` 已完成 |
| children | TaskNode[] | 子任务（递归嵌套，不限层） |
| sort_order | int | 同级排序 |
| completed_at | string | 完成时间（由完成打卡写入） |
| completed_by_slot | int/null | 由哪一格打卡完成（用于删除打卡与"取消完成"回退） |
| created_at | string | 创建时间 |

计算属性（服务端聚合，不入库）：关联打卡次数、**实际投入时长**（= Σ 关联打卡的 duration_minutes，每条全额计入）、子树完成数 x/y。

**统计铁律**：一切进度与汇总**只计算叶子节点**；父节点不重复计入。

### 3.2 卡片结构变化

```json
// card.tasks[] —— 根任务数组（替换 milestones + todos）
[
  {
    "id": "task_root1",
    "title": "个人博客网站",
    "estimated_minutes": 900,        // 自动 = Σ叶子 15h
    "status": "doing",
    "children": [
      { "id": "task_1", "title": "寻找建站工具、开源项目", "estimated_minutes": 240,
        "status": "done", "children": [], "completed_at": "2026-09-17 21:30:00", "completed_by_slot": 12 },
      { "id": "task_3", "title": "部署上线", "estimated_minutes": 360, "status": "doing",
        "children": [ /* 域名注册 / 域名解析 / 项目打包 / 宝塔部署 / 备案 */ ] }
    ]
  }
]
```

### 3.3 打卡记录扩展（多任务关联）

`slot.record` 新增 `task_links` 字段（其余字段不变，交易卡的预测/分析/余额逻辑不受影响）：

```json
{
  "content": "调研 Hugo 和 WordPress 并写了对比笔记",
  "duration_minutes": 60,            // 打卡总时长（不变）
  "task_links": [                    // 可暂为空（待关联）；结束时补选，见 Q11
    { "task_id": "task_1", "state": "done"  },   // 本次完成
    { "task_id": "task_2", "state": "doing" }    // 本次推进（进行中）
  ]
}
```

- `state`：本次打卡对该任务的标记（`doing` / `done`）；**每个任务独立标记**（Q14）
- **不做时长分摊**（Q13）：每个关联任务按打卡 `duration_minutes` **全额**计入"实际时长"
- `task_links` 为空 = **待关联**（打卡开始时未选 / 历史打卡），界面持续提醒，可随时补选
- 不能关联已完成的任务（Q5）
- 历史打卡（迁移前）同样显示「未关联」，支持补选关联，不影响任何统计

### 3.4 状态语义

- `todo`：默认；出现在任务树上，未开始
- `doing`：首次被打卡关联时自动置为进行中
- `done`：**只能由打卡标记**（含 §4.3 父级自动上卷）；树上不提供勾选
- 可被打卡关联的节点 = **叶子节点** 且 `status ∈ {todo, doing}` 且预估已填
- 「待关联」不是任务状态，是**打卡的关联状态**（task_links 为空）

## 4. 关键规则

### 4.1 层级与操作（FR-1）

- 层级不限；任意节点可添加子任务（UI 至少稳定支持 3 层折叠展开）
- 节点操作：＋子任务 / 编辑名称 / 改预估 / 删除（级联子树，前端二次确认）/ 上移下移（Q12）
- 一个叶子节点新增子任务后变为容器：自身预估清零（改由 Σ子 汇总），历史打卡关联保留
- 删除节点时其关联打卡**记录保留**（显示为「已删除任务」）
- **进行中的任务卡**：节点名称、时长、结构等全部可编辑【Q10】
- **已结束的卡**（completed / failed / abandoned）：任务树只读，防误改历史

### 4.2 预估工作量（FR-2）

- **叶子任务预估必填**（Q3）；界面按小时输入、支持 0.5h 粒度，存储用分钟
- 新增任务时提供快速选项（0.5h / 1h / 2h / 4h / 8h / 自定义）
- 父任务预估自动 = Σ 叶子，只读展示
- 迁移产生的历史节点标「⚠️ 待补预估」：不计入进度、不可被打卡关联，补全后自动恢复

### 4.3 完成规则（FR-3）

1. 完成**只能通过打卡标记**；树上无勾选【Q5】
2. 子任务全部 `done` → 父任务**自动** `done`（逐级连锁上卷）【Q6】
3. 已完成的任务**不能再被打卡关联**（打卡选择器中不出现已完成任务）【Q5】
4. **取消完成**：树上提供快捷入口【Q15】——点击后反查该任务的完成依据打卡，把其中该任务的状态改回"进行中"，已完成上卷的父任务同步回退

### 4.4 打卡联动（FR-4，核心）

**打卡两步流程**（贴合真实工作节奏，Q11）：

```
① 开始打卡：点格子 → 填写内容 + 时长（可设 0 = 刚开始）→ 保存
   → 打卡进入"进行中"，暂不选任务（允许待关联）
② 结束打卡：工作完成 → 回到该打卡 → 更新实际时长
   + 选择关联任务（树形多选，引导必选 ≥1）+ 每个任务独立标记状态（进行中/已完成）
   → 任务状态联动（doing / done + 上卷），打卡闭环
```

- 一次性补记（如历史补录）：一步填完内容 + 时长 + 任务 + 状态即可
- 任何未关联任务的打卡显示「⚠️ 未关联任务 [去关联]」提醒，可随时补选（含历史打卡）
- 若卡片暂无可用任务节点 → 弹窗内提供「快速新建任务」引导（名称 + 预估必填）

服务端联动规则：

| 场景 | 行为 |
|------|------|
| task_links 为空 | 允许保存（待关联）；界面提醒补选，不计入任务实际时长 |
| 任务被标记 `done` | 节点置 done，写入 completed_at / completed_by_slot，触发父级上卷 |
| 任务被标记 `doing` | 节点为 `todo` 时自动置 `doing` |
| 已完成的任务被再次关联 | **服务端拒绝**（"该任务已完成，不能继续打卡"）【Q5】 |
| 删除打卡（unfill） | 该打卡标记完成的任务全部回退 `doing`；已上卷的父任务同步回退【Q7】 |
| 取消完成（task-cancel-done） | 反查完成依据打卡，将对应 task_link 改回 doing + 上卷回退【Q15】 |
| 修改打卡（update-slot） | 支持补充/修改关联任务集合与各任务状态（结束打卡的主要路径）；同步执行上卷/回退 |
| 批量补录（单点/范围） | 整批统一选择关联任务（可多选），状态统一为「进行中」；需要标完成的日期，事后在单条记录里单独修改 |

服务端一致性校验：task_links 非空时，task_id 必须存在、是叶子、状态可打卡；`state=done` 时该任务必须尚未完成。

### 4.5 任务进度计算（FR-6）

```
任务进度 = Σ(状态=done 的叶子任务预估分钟) ÷ Σ(全部叶子任务预估分钟)
```

- 只统计叶子；父节点不重复计入
- 与打卡实际时长无关（口径 = "任务做完了没"；完成 1+2 个 4h/5h 任务即 60%）
- 显示：百分比取整 + 明细"已完成 9h / 15h · 2/3 个任务"
- 无任务树时：退回只显示工时进度（格数/100）

### 4.6 实际 vs 预估对比（FR-5）

- 每个叶子任务显示：`预估 4h · 实际 3.5h`
  - **实际 = Σ(关联打卡的 duration_minutes)，每条打卡全额计入（Q13，不做分摊）**
  - 例：1h 打卡同时关联 A、B → A 实际 +1h、B 实际 +1h
- 超预估仅提示、不施加惩罚（长期主义：只报喜不施压）
- 卡片顶部汇总：`任务工作量 15h · 累计打卡 12h`（打卡总时长不重复计算，与节点实际之和口径不同，界面标注）

### 4.7 与工时 / 奖励体系的关系（FR-7）

- 100 格打卡、在场统计、连续在场、奖励结算口径**全部不变**
- 学习卡"子目标全部完成可提前通关" → 改为"**任务树全部完成**（所有叶子 done）可提前通关"
- **打卡满 100 格自动结算通关（现状不变）**；若任务树尚未完成，随卡结束、保留只读可查看【Q16】
- 交易卡结算仍按资金倍数；分析纪律闸门（先分析再打卡）不受任务树影响

## 5. 界面需求

### 5.1 任务树展示（卡详情）

- 位置：概览 Tab 与独立「🌳 任务」Tab **均展示**任务树（Q11）；原"目标拆解 / 待办清单"两个区块移除
  - 概览 Tab：内嵌任务树（可折叠、含进度与快捷操作）
  - 「🌳 任务」Tab：完整管理视图（双进度条 + 全树 + 统计）
- 树形列表节点行示意：

```
[▾] ✅ 个人博客网站（容器）      总进度 ████████░░ 60%  9h/15h · 2/3 任务
      ✅ 任务1 寻找建站工具、开源项目   预估4h·实际2.5h  🕐3次  [＋][✏️][🗑]
      ✅ 任务2 确定目标网站…           预估5h·实际4h    🕐2次  [＋][✏️][🗑]
      [▸] ◐ 任务3 部署上线（=Σ子 6h）  子进度 1/5              [＋][✏️][🗑]
```

- done：✅ + 划线；doing：◐；todo：○；待补预估：⚠️；done 节点带「取消完成」操作（Q15）
- 点击节点可查看该任务的打卡记录（或打卡列表按任务筛选）

### 5.2 打卡弹窗

- **开始打卡**：内容 + 时长（可 0）；任务关联区可留空（稍后再选）
- **结束打卡**：更新实际时长 + 关联任务树形多选（引导必选 ≥1）+ 每任务状态单选（进行中/已完成）
- 支持一次性补记（内容 + 时长 + 任务 + 状态一步完成）
- 学习卡与交易卡一致；单点/范围补录同样支持（整批统一选）

### 5.3 打卡记录列表

- 每条显示任务标签：`[任务2 · 确定目标网站]`
- 未关联任务的打卡显示 `⚠️ 未关联任务 [去关联]`（含历史打卡，可补选）
- 格子 tooltip 同步显示所属任务

### 5.4 进度条与对比

- 卡片列表 & 卡详情：**双条** —— 任务进度（主）+ 工时进度（格数/100，辅），标注清楚
- 任务树每个容器节点显示子树进度（x/y 完成）
- 卡详情顶部："任务工作量 15h · 累计打卡 12h" 汇总对比

## 6. API 变更草案

| 接口 | 变更 | 说明 |
|------|------|------|
| `GET /plan/api/card-detail` | 修改 | 返回 `tasks` 任务树 + 任务进度 + 各节点实际时长聚合 |
| `POST /plan/api/task-add` | 新增 | 新增节点 `{parent_id?, title, estimated_minutes}` |
| `POST /plan/api/task-update` | 新增 | 改名称/预估/排序/移动层级（parent_id） |
| `POST /plan/api/task-delete` | 新增 | 删除节点及子树；容器预估自动重算；关联打卡保留 |
| `POST /plan/api/task-cancel-done` | 新增 | 取消完成：反查完成依据打卡，将对应 task_link 改回 doing + 上卷回退 |
| `POST /plan/api/fill-slot` | 修改 | `record.task_links` 可为空（待关联）；非空时严格校验 + 状态联动 + 上卷；响应附带任务树刷新 |
| `POST /plan/api/update-slot` | 修改 | **结束打卡主要路径**：更新时长 + 补充/修改 task_links；同步上卷/回退 |
| `POST /plan/api/unfill-slot` | 修改 | 完成依据打卡被删 → 相关任务回退（含上卷父任务） |
| `POST /plan/api/backfill-batch` | 修改 | 批量补录统一指定 task_links（状态固定 doing，可多选任务） |
| `POST /plan/api/settle-round` | 修改 | 学习卡提前通关判定改为"任务树全部完成" |

## 7. 数据兼容与迁移（FR-8）

1. **惰性迁移（幂等）**：加载时若卡片无 `tasks` 键 → 将 `milestones` 与 `todos` 自动转为任务树顶层节点（`content → title`；`done → status`；预估留空并标「待补预估」）
2. 迁移节点：进行中的卡可自由补预估/改名/调整结构；补全预估前不计入进度、不可被打卡关联
3. 旧字段 `milestones` / `todos` 列**保留只读归档**一版，后续批次沿用 `_drop_legacy_columns` 模式统一清理
4. 表结构变更：
   - `plan_cards` 加列 `tasks TEXT`（JSON 整树）
   - `plan_slots` 加列 `task_links TEXT DEFAULT '[]'`（JSON 数组：`[{task_id, state}]`）
   - 存量库通过 `database.py` 的 `_REQUIRED_COLUMNS` 自动补列 + `db_schema.sql` 同步（沿用现有机制，免手工 SQL）
5. 历史打卡无 task_links → 显示「未关联」（可补选），不影响统计

## 10. 影响面与风险

- **影响文件**：`plan_routes.py`（打卡联动/上卷回退/取消完成/提前通关判定/摘要）、`plan_repo.py`（tasks 与 task_links 列差量同步）、`models.py`（PlanCard.tasks、PlanSlot.task_links）、`database.py`（列补丁）、`db_schema.sql`、`task_plan.js` / `task_plan.html`（双重位置任务树、打卡弹窗两步流程、待关联提醒、记录标签、双进度条）
- **风险 1**：双口径（任务工作量 vs 打卡时长）易混淆 → UI 明确标注，汇总处并列展示
- **风险 2**：多任务全额计时（Q13）→ 节点实际之和可大于打卡总时长，界面标注口径说明，避免误读为数据错误
- **风险 3**：任务树工作量 > 100 格时满卡先通关（Q16-A）→ 任务树随卡冻结只读，剩余任务可开新卡承载（二期可考虑结转）
- **风险 4**：迁移节点「待补预估」期间的进度显示 → 明确标注「待补」不计入进度
