# 批量趋势更新提速优化方案

> 状态：**待确认，未改代码**。本方案仅规划，确认后再实施。
> 目标：在不减少「55 币种 × 4 周期 = 220 个组合」覆盖的前提下，把"批量更新趋势数据"的耗时显著降下来，并把请求频率钉死在 OKX 安全线内。

---

## 0. 实测依据（2026-09-17，本机直连 OKX 生产）

用项目实际 SDK（`okx.MarketData`）与 httpx 直连主站实测：

| 接口 | 用途 | `limit=300` 实测 | 返回 code |
|---|---|---|---|
| `get_candlesticks`（成交价K线） | — | 返回 **300 根** | 0 |
| `get_index_candlesticks`（指数K线） | 当前 SAR/ER 取数 | 返回 **300 根** | 0 |
| `get_mark_price_candlesticks`（标记价K线） | 当前趋势取数 | 返回 **300 根** | 0 |

补充结论：
- **单次请求最大 limit = 300**（默认 100）。三个行情接口一致。→ "500 根"只能靠翻页，不是单次能取的。
- 公共行情接口本次**未返回 `x-ratelimit-*` 响应头** → 无法靠响应头自适应降速，必须用**进程内令牌桶主动限频**。
- OKX 市场数据按 **IP 限流**（无需鉴权也吃 IP 配额），量级约"每接口 ~100 请求/2 秒"，另有全局硬顶；超限回 `50011`/HTTP `429`，属**临时拒绝**（退避即恢复），**不是封 IP**。

## 1. 现状与根因

### 1.1 单个组合现在要发几次请求

当前每个 `(instId, bar)` 组合的取数：

| 取数 | 接口 | 条数目标 | 页数（limit=300） | 请求次数 |
|---|---|---|---|---|
| 趋势主取数 | 标记价K线 | 500 | ⌈500/300⌉ = 2 | **2** |
| SAR + ER | 指数K线 | 100 | 1 | **1** |
| 合计 | | | | **3 次/组合** |

→ 220 组合 ≈ **660 次请求**（弱网触发重试/翻页只回100时会更多）。

相关代码：
- 趋势翻页：`crypto/strategy/pro3_singletimeframe.py` `_fetch_kline_data` / `_KLINE_TARGET_COUNT=500`
- SAR 单独取指数K线：`crypto/batch_trend_updater.py` `_process_single_symbol` 第二段循环 + `_fetch_klines_for_sar`

### 1.2 四大根因（按影响排序）

1. **开了 3 线程，但主链路仍在锁内串行。**
   `real_strategy_adapter.calculate_single_coin_data` 被 `@pro3_locked` 整段包住，包住的范围**同时含"等网络 + 下载多页K线 + backtrader 回放"**。A 币在等交易所响应时，B/C 币也得排队。加密 worker 数解决不了这个瓶颈。
   （锁本身不能删：pro3 引擎用模块级全局 `FAST_MODE/PRINT_*/CURRENT_*`，并发会串味。）

2. **SAR/ER 白取了 220 次指数K线。**
   SAR 只需 High/Low/Close、ER 只需 Close，**这些在趋势那份标记价K线里都有**，与 MACD/ADX 同源同算法。当初分开取仅仅是"换了指数价口径"，而 SAR/ER 只是表格辅助列、不参与下单判定。→ 可直接从同一份K线算出，省掉整批 220 次请求。

3. **缓存过期即全量重下。**
   趋势缓存 TTL=60s、且过期后重新分页拉满 500 根。但一次更新真正变化的只有"未收盘的那根 + 上次之后新增的几根"，前面几百根历史无需重下。

4. **每个组合都跑完整历史回放。**
   即使行情备好，220 次 backtrader 逐根回放（写 DataFrame、算零点、模拟交易、假信号统计）仍占可观时间。此项为**锁内计算**瓶颈，需在 1 拆锁后才凸显。

次要：每完成 5 个币种全量写一次 DB+CSV（55 个 → 11 次整表覆盖写）。

## 2. 优化方案

### 决策 D1：趋势目标K线数 500 → 300（单次一页搞定）

- 依据：实测单页可取满 300 根；MACD(12/26/9)、ADX(14)、ATR(14)、SAR 的暖机约 30~60 根即收敛，300 根对**方向/指标值**足够。
- 收益：趋势主取数 2 页 → **1 页**，每组合少 1 次请求。
- ⚠️ **风险与门槛**：缩短历史会改变回放起点，可能影响 **`交易价格/交易时间/盈亏%`** 这三列——若某币"最近一次交易信号"发生在 300 根之前，截断后取不到。方向/MACD/ADX/ATR 基本不变。
- **强制 A/B 验证**：实施后必须用生产真实数据，同一份行情分别按 500 与 300 计算，逐币比对趋势方向、交易价、交易时间、盈亏四列；差异不可接受则回退保留 500（走 D3 增量后，500 也只需 1~2 次请求，成本已可控）。

### 决策 D2：SAR/ER 改为从趋势标记价K线直接计算，删除指数K线请求

- 做法：`_process_single_symbol` 里，SAR/ER 复用第一段已经拿到的趋势K线（`get_latest_data` 返回/或 `_fetch_kline_data` 的 df），删掉第二段 `_fetch_klines_for_sar` 的整批调用与 `_sar_kline_cache`。
- 口径变化：SAR 颜色、ER 从"指数价基准"改为"标记价基准"，与趋势列同源、更自洽；仅影响展示列，不影响下单判定。
- 收益：**直接省掉 ~220 次请求**（约占总量的 1/3，D1+D2 后从 660 → 220）。
- 备选（若坚持保指数价口径）：指数K线走 D3 的长 TTL 缓存 + 并发预热，不再每轮重取。

### 决策 D3：缓存改为"增量复用 + 分级 TTL"，过期只补最新一页

- 分级 TTL（按"一根K线多久走完"设定"新鲜期"，新鲜期内 0 请求直接复用）：

  | 周期 | 一根时长 | 建议 TTL | 说明 |
  |---|---|---|---|
  | 15m | 15 min | 60~90s | 未收盘线分钟级在动 |
  | 1H | 60 min | 2~3 min | |
  | 4H | 240 min | 5 min | |
  | 1D | 1 day | 10~15 min | 收盘前变化很小 |

- 增量合并：缓存命中且未过期 → 0 请求；过期 → **只请求最新一页(≤300 根)**，按时间戳覆盖/去重/合并进已有历史，发现缺口再补翻页；不再无脑重下整段。
- 稳态效果：**每个组合每次到期更新 ≈ 1 次请求**（D1 已使一页覆盖全部目标，配合合并基本等于刷新最新页）。

### 决策 D4：拆锁并发——"下载"与"锁内计算"解耦（最关键的一步）

**流水线模型**：

```
并发下载阶段（受令牌桶限频，不占 PRO3_LOCK）
   对每个 (instId,bar) 预热K线 → 写入本轮 run 级缓存
            │  (下载好一个入队一个)
            ▼
串行计算阶段（在 PRO3_LOCK 下）
   get_latest_data 命中已预热缓存(0网络) → 只做 backtrader 计算
```

- 关键实现取向：把 `_fetch_kline_data` 的取数在**锁外并发预热**，`get_latest_data` 计算时直接命中缓存；锁的持有时间从"网络+计算"缩到"纯计算"。
- 本轮 run 内预热用的缓存要**活到被计算为止**（用 run 作用域缓存，或确保 TTL ≥ 下载总时长；不能"预热完就过期又被重下"）。
- ⚠️ **注意与既有决策的冲突，需你点头**：`pro3_singletimeframe._request_candles` 是实盘交易主链路，历史上被**有意未接限频**（见 `crypto/task/utils/okx_ratelimit.py` 顶部说明）。本方案要求给"**批量**路径的取数"接上共享令牌桶——实现上应只对批量场景生效，**不给实盘主链路新增任何可能卡住取数的环节**（例如通过参数开关，批量走限频、实盘走原直连）。这是必须遵守的边界。

### 决策 D5：限频安全——统一令牌桶 + 保守速率

- **单一共享桶**：趋势取数与（若保留的）指数取数**共用同一个 `market_candles` 桶**，因为都是同一 IP 配额，分开限会叠加超限。
- 速率取值：维持现有保守 **~5 请求/秒**（约官方上限的 1/10），worker 并发 **4~6**。提速靠"下载与计算重叠的流水线"，**不靠堆线程冲速率**。
- 退避兜底：命中 `50011/429` 时走 `okx_ratelimit.limited()` 已有的**指数退避+抖动**；拿不到令牌 `RateLimited` → 该币本轮降级跳过，不雪崩重试。
- 因本次实测公共接口无 `x-ratelimit-*` 头，**不实现"读头自适应"**，主动限频即可。
- 结论：在 ~5/s + 并发≤6 + D1/D2/D3 把稳态请求压到 ~220 甚至更低的前提下，远低于 IP 限流线，**不会封 IP**。

### 决策 D6：保存降频（次要，随手做）

- 整表 DB 覆盖写 + CSV 双写从"每 5 个币种"改为"**每 N（如 15~20）个或任务结束各一次**"，减少全量重写次数。
- 保留"任务结束必写一次"，避免中途失败丢结果。

## 3. 请求量与耗时对比

| 场景 | 每组合请求数 | 220 组合总请求 | @5/s 纯网络时间 |
|---|---|---|---|
| **现状**（2页趋势 + 1页指数；主取数还不限速） | 3 | ~660 | ~132s（且无节流保护，易触发退避更慢） |
| **D1+D2 强制全刷**（1页趋势；SAR本地算） | 1 | ~220 | ~44s，受桶保护 |
| **再加 D3 增量/分级TTL** | 到期才 1 | 远低于 220 | 更低 |
| **D4 流水线** | — | — | 网络与计算重叠，墙钟时间趋近 max(下载流水, 串行计算) 而非相加 |

> 锁内计算(220 次回放)的耗时在 D4 后成为新下限；若实测发现计算占大头，二期再评估"增量计算/减少逐根 DataFrame 写入"（需同一份行情做结果一致性回归，另立方案，本方案暂不含）。

## 4. 实施步骤（确认后才执行；均为改动，非新增服务）

1. `batch_trend_updater.py`
   - 删 SAR 的指数取数，改从趋势K线算 SAR/ER（D2）。
   - `run()` 改两段式：先并发预热下载（走共享桶，D4/D5），后在 `pro3_locked` 下串行计算（D4）。
   - 计算阶段 `_fetch_kline_data` 命中 run 级预热缓存，锁内 0 网络。
   - 保存降频（D6）。
2. `pro3_singletimeframe.py`
   - `_KLINE_TARGET_COUNT` 500→300（D1，需过 A/B）。
   - 分级 TTL + 增量合并（D3）。
   - 取数限频接入：**仅批量路径**经 `market_candles` 桶，实盘主链路保持直连（D4/D5 边界）。
3. 验证
   - **A/B 回归（D1 门槛）**：生产真实数据，500 vs 300 逐币比对方向/交易价/交易时间/盈亏四列。
   - **限频压测**：整轮批量下，记录 `market_candles` 桶 `throttled/refused` 计数应≈0、无 `50011`。
   - 冒烟：`_smoke_okx_ratelimit.py` 静态扫描覆盖新增取数调用点已接线。
   - 端到端：页面点"批量更新"，比对前后耗时与结果行数/正确性。

## 5. 决策点（已确认 2026-09-17）

- **A. SAR/ER 口径 → 已确认：采用 D2，改用标记价。**
  澄清：OKX 合约页最大的当前价是「最新成交价 last」，标记价/指数价在小字区单独展示（指数价=多所现货基准，用于锚定标记价与资金费率；标记价=强平/未实现盈亏用）。
  **本系统策略引擎本就跑在标记价上**（趋势取数 `get_mark_price_candlesticks`），趋势方向/现价/盈亏/MACD/ADX/ATR 全是标记价口径，当前仅 SAR/ER 例外用了指数价。故 D2 让 SAR/ER 回归与趋势列、与实盘交易基准同源，无负面影响。
- **B. 500→300 → 已确认：改为 300。** 仍以第 4.3 的 A/B 回归为落地门槛（比对方向/交易价/交易时间/盈亏四列）；若个别币因"最近交易信号早于 300 根前"导致取数差异不可接受，回退保留 500，靠 D3 增量压成本。
- **C. 给批量取数接限频 → 已确认：可以。** 边界：仅批量路径经 `market_candles` 共享桶，实盘主链路 `pro3._request_candles` 保持原直连不受影响（参数开关隔离）。
- **D. 分级 TTL → 已确认：按第 2 节 D3 表执行**（15m=60~90s / 1H=2~3min / 4H=5min / 1D=10~15min）。

**决策全部确认完毕。下一步进入改代码：按第 4 节顺序实施 D1~D6，改完先跑 A/B 回归与限频压测，冒烟不过不上线。**

## 6. 实施与验证结果（2026-09-17 已落地）

改动文件：`crypto/strategy/pro3_singletimeframe.py`、`crypto/batch_trend_updater.py`。

| 决策 | 落地位置 | 说明 |
|---|---|---|
| D1 500→300 | pro3 `_KLINE_TARGET_COUNT=300` | 一页取满、免翻页；A/B 门槛已过 |
| D2 SAR/ER 同源 | batch `_process_single_symbol` + `_compute_sar_from_df/_compute_er_from_df` | 直接复用趋势标记价 df，删除 `_fetch_klines_for_sar` 指数取数调用（220 次/轮） |
| D3 分级 TTL | pro3 `_KLINE_CACHE_TTL_BY_BAR` + `_ttl_for_bar()` | 15m=90s/1H=150s/4H=300s/1D=900s；新鲜期内 0 请求 |
| D4 拆锁流水线 | pro3 `_batch_kline_cache`(+store/get/clear) & batch `run()` 两段式 | 阶段1 锁外并发预热写 run 级缓存；阶段2 锁内计算命中缓存 0 网络；`finally` 清空 |
| D5 批量接限频 | batch `_warm_kline()` 经 `_rl('market_candles', …)` | 仅批量预热路径限频；实盘 `pro3._request_candles` 保持直连不动 |
| D6 保存降频 | batch `_SAVE_EVERY=20` + 收尾兜底写一次 | 55 币 11 次 → ~3 次落库 |

**验证（均真实连 OKX 生产）：**
- 语法：两文件 `ast.parse` 通过；`GetProblems` 仅存量风格告警，无新增 error。
- A/B 回归 `data/_ab_trend_500_300.py`：**同一行情快照**上比对「全量(600) vs 最近 300」，8 币 ×4 周期共 32 组，**决策四列（趋势/交易价/交易时间/盈亏%）0/32 差异**（仅 1 组指标末位暖机噪声）。
  - 方法学要点：早先分两次联网跑 500/300 出现"profit 全不一致"，实为两次运行间现价漂移的假阳性，非历史长度所致；改为单快照裁剪对照后隔离出唯一变量，结论干净。
- 端到端冒烟 `data/_smoke_batch_pipeline.py`（3 币，不写 CSV/DB）：预热 12/12 命中 run 缓存、**计算阶段新增缓存键=0（锁内 0 网络）**、SAR/ER 12/12 本地算出、`clear_batch_cache` 清空生效；单币 15m 冷连接 ConnectTimeout 被 `_request_candles` 自带重试自愈。

**预期收益**：请求量 660→220/轮（D1+D2）；锁持有从"网络+计算"缩到"纯计算"（D4）；重复轮次内新鲜周期 0 请求（D3）；落库次数降 ~4x（D6）。

**未改动**：实盘/监控台主链路取数路径与限频接线，保持原样。
