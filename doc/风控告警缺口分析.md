# 双仓位策略 · 交易风控与异常处理 深度分析报告

> 分析对象：`crypto/task/trend_range_trader.py`（趋势跟踪 + 区间波动双仓位）
> 视角：交易风控与异常处理。本报告为纯分析，落盘时未改动任何交易代码。
> 关联通读模块：`tp_engine.py`、`utils/position_order_manager.py`、`utils/trade_executor.py`、
> `monitor/alert_monitor.py`、`notification/message_notifier.py`、`config/config_trend_range.json`。

## 〇、先厘清一个架构前提（影响所有结论）

系统当前是**两套彼此独立、互不共享数据与阈值的链路**：

| 链路 | 位置 | 节奏 | 职责 | 会不会动仓 |
|---|---|---|---|---|
| 主交易循环 | `trend_range_trader.start_real_scheduler`（线程） | 80s/轮 | 决策+执行+兜底委托 | 会 |
| 监控告警引擎 | `alert_monitor.run_alert_check`（APScheduler 任务） | 默认 **300s**/轮 | 只读行情K线+只读持仓，**只发邮件+写 alert_log** | **不会** |

关键点：`alert_monitor` 是**旁路只报警、不干预**的，它独立拉 1m K线和持仓，和主循环里"每轮已经算好的 BOLL/ATR/价格"没有任何复用关系。后面很多缺口的根因都在这里——**报警的视角和执行的视角是分裂的**。

---

## 一、现有风控/告警覆盖度盘点（"已经有什么"）

### A. 主循环内已实现（相当扎实）
- **反向持仓风控** `_check_reverse_position_guard`(L534)：检测→`grace_minutes`(默认10min)预警→超时强平，计时器 MySQL 持久化跨重启不重置；账本内旧方向残留仓 + 账本外人工反向单分别计量；预警/强平邮件**显式豁免 30min 冷却**（`send_reverse_position_warning` L383）；强平失败保留计时器下轮重试、不发"已强平"误报。
- **睡眠时段强平** `_in_night_window`(L1535) + 步骤6(L2246)：东八区 0–6 点趋势仓长周期反转才强平，白天只发提醒邮件；区间仓反转始终强平换向。
- **止盈止损**：`_check_tp_sl`(L1322) 优先级 止损→时间兜底→六类主止盈（`tp_engine`），**本地评估 + 交易所侧兜底委托双保险**(`_sync_trend_algo` L1707)。
- **冷却三件套**：止盈止损冷却 `_start_tp_cooldown`(L374)、人工强平冷却、手动平仓检测 `_detect_external_close`(L413)——防止刚平仓立即追价重开。
- **查询失败即跳过本轮**（不把"查询失败"误当"空仓"重复开仓）、**智能减仓**、**杠杆周期回核**、**仓位上限拦截**、**观察模式**(`trade_enabled=false`)。
- **连续失败升级邮件** `_note_cycle_result`(L2411)。
- **下单链路健壮性**：HTTP 超时抬到 20s、`clOrdId` 反查定性"结果未知"、限频退避、reduce-only 软件封顶、挂单 TTL 撤单、账本对账/吸收。

### B. 独立监控已实现
- **行情异动**：15min 窗口涨跌幅，warning 5% / critical 8%，级别递进状态机 + recover 缓解。
- **持仓盈亏**：单仓浮动盈亏率，warning −10% / critical −20%。

### C. 邮件通道现有能力（`message_notifier`）
交易操作、趋势反转预警/确认、反向持仓预警/强平、开仓窗口、观察模式、系统告警、行情异动、持仓盈亏、聚合摘要——共 9+ 类。

> **总体判断**：执行链路（下单/对账/兜底）健壮度很高，"程序自身决策对不对"防护得很细；**薄弱的是"外部极端行情"与"静默失效是否被看见"这两类**，而这正是四个提问的核心。

## 二、按四个维度的风险点分析

### 维度 1：价格戳破 BOLL 上下轨

**系统当前反应**
- **趋势仓**：只有 `channel` 止盈 `mode='outer'` 会在"多头价≥上轨 **且处于盈利**"时平仓（`tp_engine._eval_channel` L470）。它是**止盈动作不是预警**，且 `take_profit.enabled=false`（配置默认关）。除此之外，主循环对"价格相对布林带的位置"没有任何判定。
- **区间仓** `process_range`(L1119)：价格戳破边界只是"把 reduce-only 平仓单挂在对侧、开仓单挂入场侧，边界漂移就 amend 追价"。系统**不会因为出轨而做任何异动反应**。
- **alert_monitor**：只看 15min 涨跌幅绝对值，**完全不看价格相对 BOLL 带宽的位置**。

**缺口与风险**
1. **最危险的组合没被单独盯**：区间策略最怕"趋势启动把区间单边戳穿"。窄幅震荡带里价格小幅出轨即回（正常刷区间），但**宽幅趋势里价格一出轨就一去不回**——此时对侧平仓单永远等不到成交、逆势侧若长周期尚未反转还会持续成交。现有逻辑要等**长周期反转**才换向，而反转判定用"上一时段方向"稳定化（`_resolve_directions` L1900），**天然滞后一拍**。
2. **涨跌幅阈值与带宽脱节**：15min 涨 6% 在趋势品种是家常便饭（会误报），窄带里刚出轨 0.5% 才是危险信号（会漏报）。**绝对涨跌幅 ≠ 出轨强度**。
3. 出轨 + 睡眠时段 + 逆势持仓，三重叠加时白天只发一封反转邮件。

**功能建议**
- 主循环已持有 `boll_upper/middle/lower` 与 `atr_value`、`price`（`_check_tp_sl` ctx 里都在传）——**加"出轨强度"检测零额外接口成本**：`(price − 边界) / ATR` 或 `/(上轨−下轨带宽)` 归一化，分级；**持仓方向与出轨方向相反时升 critical**。
- 新增邮件 `send_boll_breakout_alert`：出轨方向、越界%、当时带宽、持仓与浮盈、**是否逆势**。豁免冷却。
- 可选保护动作（与 `tp_cooldown` 同机制）：剧烈出轨时临时 `range_allow_entry=False`，阻止在错误一侧继续挂开仓单，而不是只发邮件。

### 维度 2：突发暴涨暴跌（短时剧烈异动 / 插针）

**系统当前反应**
- 只有 `alert_monitor` 的 15min 涨跌幅告警，且**采样端点对端点**（`_fetch_window_change_pct` 用 `closes[0]` vs `closes[-1]`）——**一根"爆拉后回落"的插针在窗口内完成就被抹平，几乎必然漏报**。
- 主循环每轮拿到 `current_price`，但**不和上一轮价对比做突变判定**。
- 止损是 `fixed_pct=3%` 或 `N×ATR`，本地评估靠 80s 轮询 + 交易所兜底委托；**插针瞬间能救的只有交易所侧静态触发价那一层**（追踪/动能/通道/分批止盈都无法下发到交易所，见 `tp_engine.exchange_backup_levels` L253）。

**缺口与风险**
1. **检测节奏错配**：报警旁路 5min 一次，主循环 80s 一次，插针常在**秒~分钟级**完成，两边都可能抓不到。
2. 无 ATR 飙升 / 波动率突增维度。
3. 报警是 5min 后的"事后追认"，异动当下主循环并不知情，仍可能照常挂开仓单（追高/杀跌）。

**功能建议**
- 主循环维护 `{inst_id: 上一轮价/时间}`，做**单轮环比涨跌幅 + 跨轮最大摆动**检测，写详细日志，超阈值**即时**邮件（不依赖 5min 旁路）。
- `alert_monitor` 改用 `high/low`（或标记价格K线，UI 已在用 mark price）检测**影线/极值**覆盖插针；支持高频档。
- 达到 critical 异动时**联动主循环保护**：临时禁止新开仓（而非仅发邮件），日志留痕"哪一轮处于异动、当时仓位如何"，便于复盘。

### 维度 3：盈亏阈值管理（回答三个诉求）

**现状**：止盈/止损**全自动市价平仓，无人工确认环节**；`ladder` 分批止盈也是**自动 `close_partial`，不是提示**。观察模式是"整币关掉自动交易=纯人工"，缺的是"正常自动 + 关键节点人工 gate"的中间态。

**关键缺陷（必须指出）**：
- **平仓邮件不含盈亏金额**：`send_trade_operation_email`(L257) 字段只有 合约/周期/方向/时间/价格/成功——**没有已实现盈亏 USDT、没有盈亏%、没有篮子、没有持仓时长**。从邮件里**根本看不出这笔平了多少钱、赚还是亏多少**。
- **alert_monitor 的 pnl 是"浮动盈亏、未平仓、价格口径%"**，不是平仓后的已实现盈亏；也不做账户级 USDT 汇总。
- **止损/止盈平仓失败只 `task_log.error` "下轮重试"（L1379/L1432），不发邮件**——若因 51008/拒单导致止损平不掉，**止损名义在、实则没平**，这是最危险的静默失效。

**逐条建议**
| 诉求 | 结论 | 建议 |
|---|---|---|
| 人工确认环节 | 不做**同步阻塞**（破坏 7×24，人不一定在） | 改"事后即时可回执"：每笔平仓邮件**补上 realized PnL**（复用现成 `_get_position_realized_pnl` L1027）+ 篮子 + 开→平时长 + 触发原因 |
| 分批止盈提示 | 现有 ladder 是自动执行 | 做**可选"提醒型阶梯"**：命中档位发 `send_tp_approach_alert` 但仍由人决定是否手动平/切观察，介于"全自动"与"观察模式"之间 |
| 大额盈亏邮件 | **明确缺失** | 新增 `send_realized_pnl_alert`，阈值分档（如 ±50U 或账户权益 1%），**盈利到账也要报**；睡眠时段大额亏损按"叫醒级"（critical 配色 + 豁免 30min 冷却，仿反向风控做法） |

> **需求澄清（2026-09-15 确认）**：盈亏管理的目的是**提醒用户**——突发暴涨盈利了要提醒、定时任务检测到持仓盈利或亏损了也要提醒，**盈亏双向**；**具体提醒阈值全部由配置决定**（不写死）。因此 P1 的 `send_realized_pnl_alert` 与 alert_monitor 的 pnl 维度都要做成：正负两侧各自可配阈值、按账号隔离、热加载。

### 维度 4：其他必须"被看见"的环节（实盘最容易吃暗亏的地方）

> 这一节问题密度最高，且多为"**看起来正常、其实已经失效**"的静默型。

1. **挂单失败 / 被交易所拒单（P0，严重）**
   - 现状：`_place_entry`(L844)、`_place_exit`(L876) 失败**仅 `task_log.warning`，且不计入连续失败告警**——因为 `analyze_and_trade_real` 只要分析+持仓查询成功就返回 `success=True`。**结论：交易所持续拒单（51008 保证金不足 / 价格过滤 / 最小量）时，心跳日志照常，系统其实一单都没挂上，完全裸奔而无人知。**
   - 建议：下单被拒纳入失败计数/邮件；对 51xxx 错误码给专门文案；"单币连续 N 次拒单"发信。

2. **"下单结果未知" need_verify（P0）**
   - 现状：`trade_executor` 定性很完善（`_unknown_place_failure` L317，反查失败标 `need_verify=True`，提示"该单可能已落地，请人工核实"），但上层只把这串 error 塞进 warning。**不核实就重发 = 重复开仓**。
   - 建议：`need_verify=True` 单独升级为一封"可能有孤儿单落地，请核实挂单/成交"邮件。

3. **接口超时 / 限频 / 网络抖动（P1）**
   - 现状：20s 超时 + 限频退避 + probe 失败保持 PENDING，处理稳健，但**只有日志**。链路成片 `read timeout`（2026-09-11 现网）时，系统"保持不动作"却无聚合告警。
   - 建议：网络/限频异常计数，N 轮内超阈值发"OKX 链路异常"系统邮件（扩 `send_system_alert` 语义）。

4. **资金费率异常（P1）**
   - 现状：funding 只在 `task.html`/`app.py` 盈亏统计里**事后呈现**（`fundingFee`），主循环与监控**都不读 funding rate**。区间仓无限循环长期挂单，**高负费率做多 / 高正费率做空会持续被抽血**，费率尖峰常伴随极端行情。
   - 建议：持仓/开仓读 `fundingRate`/`nextFundingRate`，超阈值（如 |8h|>0.05%）发信 + 详细日志。

5. **强平价距离 / 爆仓风险（P0/P1）**
   - 现状：`liq_px`、`mark_px` 在 UI 有展示（`app.py` L2015、`task.html` L2729），**自动链路没有任何"现价逼近强平价"预警**。逐仓空头/全仓多头会被插针打到强平价。
   - 建议：按 mark 价与 `liq_px` 距离（% 或 ATR）分级预警，**睡眠时段尤其要邮件叫醒**。

6. **账户保证金率 / 可用余额健康（P1）**
   - 现状：`risk_control` 只有张数/USD 上限且默认 `10000`≈没设；不做账户权益/可用/维持保证金率巡检，余额不足只在被 51008 拒时被动发现。
   - 建议：每 N 轮拉账户概览，可用余额 / 保证金率临近爆仓 → 邮件。

7. **兜底委托"不在位"（P1）**
   - 现状：`poll_algo_triggers`(L1284) 能发现 effective/order_failed/canceled，`sync_exchange_algo` 挂失败只 warning。若交易所兜底委托长期挂不上 + 本地宕机，则完全裸奔。
   - 建议："该有的保险不在位"→ 邮件（挂失败/被撤且重挂仍失败连续 N 次）。

8. **账本与交易所大幅背离（P2）**
   - 现状：`reconcile`(L349) 按比例缩减/吸收**只 info**。突然大幅缩减可能意味着**强平/爆仓已发生**。
   - 建议：单轮缩减/吸收超阈值 → 告警 + 留痕。

9. **持久化层降级（P2）**
   - 现状：DB 不可用回退文件/回退空，都 warning。冷却/反向计时/方向记录长时间不能落库，重启即丢状态导致误判。
   - 建议：持久化降级持续 N 轮 → 邮件。

10. **调度轮"活着但卡死"（P1）**
    - 现状：心跳只在正常产轮时出现；若某轮 `analyze` hang（极端拖长）或 `_trade_lock` 被长占，则**无新轮、也无失败计数 = 静默**。`memory_watchdog`/`process_lifecycle` 管的是 OOM/重启分类，不是"本轮停滞"。
    - 建议：独立轻量 liveness——超 `execution_interval × N` 无"本轮结束"日志 → 邮件。

11. **告警通道自身失效（元问题，P1）**
    - 现状：所有告警都靠 email，`_dispatch_email` 失败返回 False 只 log；仅启动时 `test_connection`。**SMTP 中途挂掉 → 所有告警静默丢失**。
    - 建议：叫醒级告警发送失败时 ERROR 留痕 + 下次补发 / 备用通道（第二 SMTP 或 webhook）。"发信失败"本身要可见。

## 四、与现有架构衔接的落地原则

1. **"外部极端行情"类**（出轨/异动/费率/强平距离）→ 优先在 `alert_monitor` 扩展维度、复用它的级别递进状态机与聚合邮件，**别把发邮件逻辑塞进 80s 主循环拖慢执行节奏**。
2. **"执行类静默失效"类**（下单被拒、止损平不掉、need_verify、兜底不在位、liveness）→ **必须在主循环内即时告警**，不能等 5min 旁路，因为它就是"这一轮已经出事"。
3. 阈值统一进 `global_settings`（新增 `risk_alerts` 段），沿用**热加载 + 按账号隔离**；叫醒级告警**显式豁免 30min 冷却**（反向风控已有先例，照抄口径）。
4. 详细日志：扩展 `trade_operations.log` 场景化模板 + 结构化字段（盈亏 USDT、拒单码、费率、强平距离），既满足复盘，也能喂给"实盘 vs 策略对比"引擎（`trade_journal`）。
